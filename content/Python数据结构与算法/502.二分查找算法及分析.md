# 基本概念与核心思想
## 有序表的查找优化切入点
在 [[501.顺序查找算法及分析#有序表顺序查找原理与实现|有序表顺序查找]] 中，如果第1个数据项不匹配查找项，最多还有 $n-1$ 个待比对的数据项。
顺序查找并未充分利用有序表的整体有序特性，每次比对仅能排除1个元素。

**二分查找（Binary Search）** 利用有序表元素按值有序排列的特性，每次从列表正中间的数据项开始比对，从而**直接排除一半的待比对数据项**，迅速缩小查找范围。
## 查找基本流程
二分查找从有序列表的 **中间位置（midpoint）** 数据项开始比对。

若中间项恰好等于目标项，则查找成功并直接返回。

（以升序表为例）
若目标项**小于中间项**，则目标项只可能出现在列表的前半部分，**后半部分的数据项全部排除**。
若目标项**大于中间项**，则目标项只可能出现在列表的后半部分，**前半部分的数据项全部排除**。

重复上述折半比对过程，直到匹配成功或待比对子表范围缩小为空（查找失败）。
# 二分查找的循环实现
## 双指针迭代代码实现
通过维护左边界下标 `first` 与右边界下标 `last` 两个游标变量，在原列表上动态收缩待比对区间。
```python
def binarySearch(alist, item):
    # 定义局部变量 first（整数），初始化为左边界起始下标 0
    first = 0
    # 定义局部变量 last（整数），调用 len() 内置函数获取列表长度属性并减 1，初始化为右边界末尾下标
    last = len(alist) - 1
    # 定义局部变量 found（布尔型），标记是否找到目标项
    found = False

    # 循环遍历：当左边界下标小于等于右边界下标（区间非空）且未找到目标项时持续循环
    while first <= last and not found:
        # 使用 // 整除运算符计算当前搜索区间的中间位置下标 midpoint
        midpoint = (first + last) // 2
        # 访问 alist 列表对象的中间元素 alist[midpoint]，与目标项 item 进行值比对
        if alist[midpoint] == item:
            found = True
        else:
            # 缩小比对范围：若目标项小于中间项，说明目标在左半区
            if item < alist[midpoint]:
                # 将右边界游标 last 收缩至中间位置左侧一位
                last = midpoint - 1
            else:
                # 若目标项大于中间项，说明目标在右半区，将左边界游标 first 推进至中间位置右侧一位
                first = midpoint + 1

    # 返回最终查找状态布尔值
    return found

# 定义升序测试列表对象 testlist
testlist = [0, 1, 2, 8, 13, 17, 19, 32, 42]

# 调用 print() 内置函数输出调用 binarySearch() 自定义函数的结果
print(binarySearch(testlist, 3))   # 目标项 3 不存在，输出 False
print(binarySearch(testlist, 13))  # 目标项 13 存在，输出 True
```

>[!notes] 循环实现核心要点
>`first` 与 `last` 局部变量：分别指向当前有效查找区间的首尾下标，构成闭区间 `[first, last]`。
>`//` 整除运算符：Python 3 中用于整数向下取整除法，确保计算出的 `midpoint` 为合法的整型（`int`）下标。
>`last = midpoint - 1` 与 `first = midpoint + 1`：由于 `alist[midpoint]` 已经完成比对且确认不匹配，收缩区间时必须跨过 `midpoint`，否则在边界情况下会导致死循环。

# 分而治之与递归实现
## 分治策略思想
二分查找算法体现了解决复杂问题的典型策略：**分而治之（Divide and Conquer）**。
[[407.分治策略|分治策略]]将原问题分解（split）为若干个规模更小、结构与原问题相似的子问题（Subproblem）。
通过递归地解决每一个小规模子问题，并将子问题的结果汇总合并（merge），最终得到原问题的解。

## 二分查找的递归实现
递归算法是分治策略最自然的表达方式，二分查找非常适合用[[401.什么是递归|递归]]函数实现。
```python
def binarySearch(alist, item):
    # 递归结束条件（基本情况）：调用 len() 内置函数判断列表长度是否为 0（空表）
    if len(alist) == 0:
        return False
    else:
        # 使用 // 整除运算符计算当前列表的中间下标 midpoint
        midpoint = len(alist) // 2
        # 访问中间元素 alist[midpoint] 与目标项 item 比对
        if alist[midpoint] == item:
            return True
        else:
            # 缩小规模并递归调用自身 binarySearch() 函数
            if item < alist[midpoint]:
                # 对列表对象执行 [:midpoint] 切片操作，截取左半部分子列表传入递归函数
                return binarySearch(alist[:midpoint], item)
            else:
                # 对列表对象执行 [midpoint+1:] 切片操作，截取右半部分子列表传入递归函数
                return binarySearch(alist[midpoint+1:], item)
```

>[!tips] 递归三要素对齐
>**结束条件（基本情况）**：`len(alist) == 0`（子表为空，查找失败返回 `False`）或 `alist[midpoint] == item`（命中目标，查找成功返回 `True`）。
>**缩小规模**：通过列表切片 `alist[:midpoint]` 或 `alist[midpoint+1:]` 将待查找列表规模减半。
>**调用自身**：在返回语句中直接调用 `binarySearch()` 函数处理减半后的子列表。
# 二分查找算法复杂度分析
## 比对次数与剩余规模推导
在二分查找中，每次比对都将下一步的待比对范围 **缩小一半**。

![[file-20261107205613358.png|210]]
## 时间复杂度求解
当比对次数 $i$ 足够多以后，待比对范围内最终将仅剩余 $1$ 个数据项。
无论这最后 $1$ 个数据项是否匹配目标项，比对过程都会在此结束。
由此可列出最大比对次数 $i$ 满足的方程：

$$\frac{n}{2^i} = 1$$

对等式两边取以 $2$ 为底的对数，求解得到：

$$i = \log_2(n)$$

因此，按核心比对次数衡量，二分查找的算法时间复杂度为 **$O(\log n)$**（对数阶）。
# 二分查找的进一步考虑与权衡
## 递归实现中的列表切片开销
虽然根据元素比对次数得出二分查找的时间复杂度为 $O(\log n)$，但在上述递归实现中存在一个隐式开销：
`binarySearch(alist[:midpoint], item)` 调用中使用了 Python 的 **列表切片（slice）** 操作。

在 Python 中，列表切片`alist[:midpoint]` 
需要拷贝元素以创建新列表，其时间复杂度为 **$O(k)$**（其中 $k$ 为切片长度）。
这会使递归版二分查找的实际总时间复杂度高于纯对数阶。
>[!attention] 消除切片开销的工程优化
>课件中采用切片写法主要是为了增强代码可读性。
>在实际工程实现中，若既想使用递归又要避免切片的时间与空间开销，可以将列表的起始索引 `first` 和结束索引 `last` 作为参数传入递归函数（如 `binarySearch(alist, first, last, item)`），始终在原列表引用上通过索引定位，从而保证严格的 $O(\log n)$ 时间复杂度和 $O(1)$ 辅助空间（不含调用栈）。
## 排序开销与实际应用场景权衡
尽管二分查找在单次查找的时间复杂度 $O(\log n)$ 上显著优于顺序查找的 $O(n)$，但二分查找的前提是 **数据项必须有序**，因此必须考虑 **对数据项进行排序的额外开销**（通常排序算法的时间复杂度为 $O(n \log n)$ 或 $O(n^2)$）。

如果数据集在 **一次排序后可以进行多次查找**，那么单次排序的高昂开销就可以被后续大量的查找操作摊薄，此时采用“先排序 + 二分查找”非常划算。
如果 **数据集经常变动（频繁插入、删除）且查找次数相对较少**，维护列表有序性的成本极高，那么直接采用 **无序表加上顺序查找** 反而更加经济高效。

因此，在算法选择的问题上，不能仅凭理论时间复杂度的优劣做决定，还必须结合数据规模、变动频率与查找频次等 **实际应用场景** 进行综合权衡。
