# 查找算法的复杂度演进
## 从无序查找遍历到折半排除
查找算法的本质是根据目标键值在数据集中定位元素。

在普通的[[313~314.无序表抽象数据类型及其python实现|无序列表]] 中，由于对数据分布完全没有**先验知识**，只能进行顺序查找，最坏时间复杂度为 $O(n)$。

若数据集已预先按大小排序，算法便掌握了元素相互排列关系的先验知识，可以通过[[502.二分查找算法及分析|二分查找]]每次排除一半区间，将复杂度降低至 $O(\log n)$。
## 散列的目标：$O(1)$ 常数级查找
二分查找虽然大幅提升了效率，但每次判断依然不可避免地依赖于**键值比对（Key Comparison）** 的算力开销。

>[!question] 键值比较开销
>在传统的查找算法（如顺序查找、二分查找）中，你每次判断“是不是这个数”，都需要让 CPU 执行一次**比较操作**（如 `target == element` 或 `target < element`）
>而**比较操作需要消耗算力**：如果数据是简单的整数，比一次只要一个 CPU 指令周期；
>但如果数据是长字符串（如一段 DNA 序列、长文章、大 JSON 对象），计算机比对两个对象是否相等需要从头到尾逐字节比较，开销很大。
>**比较次数决定耗时**：二分查找虽然快，但在 100 万条数据中仍需比对约 20 次；顺序查找平均要比对 50 万次。
>**散列的目标**：散列想做到“**零比较或极少比较**”——不把目标和表里的其他数据挨个对比，而是直接算出一个位置去拿，省去反复比较带来的开销。

为了将查找次数彻底压缩至常数级别 $O(1)$，需要引入一种全新的数据结构：**散列表**。
通过直接建立“数据项的值”与“物理存储位置”之间的对应关系，使得查找时无需反复比对，直接一步定位，这种机制称为 **散列（Hashing，又称哈希）**。
# 散列的核心概念与思想
## 什么是散列
散列是一种通过特定计算，将数据项的**键值（Key）** 直接转换为内存中**具体存放位置（Index / Address）** 的寻址技术。（直接寻址技术）
如果事先能够知道要查找的数据项应当出现在数据集中的哪一个确切位置，就可以直接到该位置检验数据项是否存在。（先验知识）
>[!notes] 先验知识的极致利用
>顺序查找：没有任何关于位置的先验知识，只能逐项比对 ($O(n)$)。
>二分查找：拥有数据已排序的先验知识，折半排除 ($O(\log n)$)。
>散列查找：拥有数据值与存放槽号强绑定的映射规则，按图索骥 ($O(1)$)。
# 散列表与槽（Slot）
## 散列表（Hash Table）
**散列表是一种特殊组织的数据集合，其内部采用特别有利于快速定位的存储方式。**

Python 中的核心内置结构 `dict`（字典）与 `set`（集合）底层均是基于散列表机制构建。
（而动态数组 `list` 则是基于连续内存物理偏移寻址。）
## 槽（Slot）与初始化
散列表内部划分的一个个具体存储单元称为 **槽（Slot）**。
每个槽拥有一个唯一的标识名称，在工程实现中通常直接对应为连续存储列表的整数索引下标（如 $0 \sim 10$）。
在数据项插入之前，每个槽的初始状态均为 `None`，代表空槽。

# 散列函数与求余法
## 散列函数（Hash Function）
实现从“数据项的值”到“存储槽名称（下标）”转换的映射函数称为散列函数，通常记作 $h(\text{item})$。
散列函数接收**数据项**作为**入参**，**输出**合法范围内的整数**槽号**。
## 求余数法（Division / Remainder Method）
求余数法是散列设计中最基础且通用的**映射手段**。‘

算法将数据项数值直接除以散列表大小（长度）并提取余数：
$$h(\text{item}) = \text{item} \pmod{\text{TableSize}}$$

>[!question] 为什么映射必然采用求余运算
>1. **避免索引越界**：待存数据项的值往往可能极大（如身份证号或上万的整数），而物理分配的散列表大小是有限的（如 11 个槽）。
>2. **数学性质保证**：任何正整数除以 $M$，所得的余数在数学上天然且必然严格落在区间 $[0, M-1]$ 之间，正好契合底层列表的有效下标范围。

>[!attention] 散列表容量为何倾向于选取质数
>表大小（$\text{TableSize}$）若选取合数（如 10），当输入数据存在公差规律（如全为偶数 2, 4, 6… 或 5 的倍数）时，数据与表容量存在公约数，会导致余数只能出现在特定的偶数槽中，奇数槽完全空置并引发大量冲突。
>选取 **质数（Prime Number）** 作为表容量，除了 1 和自身外没有其他公因子，能够最大限度打散输入数据的内在周期性规律，使槽位分布均匀。
# 负载因子与查找性能
## 负载因子（Load Factor）
槽被数据项占据的比例称为散列表的负载因子，通常记作 $\lambda$：
$$\lambda = \frac{\text{当前已存数据项个数}}{\text{散列表总槽数}}$$
例如 11 个槽中存入了 6 个元素，当前负载因子 $\lambda = 6 / 11 \approx 0.545$。
负载因子是衡量散列表空间利用率与冲突剧烈程度的核心指标。
## 查找流程与常数复杂度
查找某数据项是否存在时，使用完全相同的散列函数 $h(\text{item})$ 计算目标槽号。
直接读取该槽号内容，判断是否与待查元素相等。
理想情况下无需遍历其他元素，单次操作时间复杂度为 $O(1)$。
# 散列表的示例
本例中我们的散列函数是最简单的求余：
h(item)= item % 11
按照散列函数h(item），为每个数据项计算出存放的位置之后，就可以将数据项存入相应的槽中。
![[file-20261109220122172.png|163]]
例子中的6个数据项插入后，占据了散列表11个槽中的6个。
槽被数据项占据的比例称为散列表的“负载因子”这里负载因子为6/11。
数据项都保存到散列表后，查找就无比简单。

要查找某个数据项是否存在于表中，我们只需要使用同一个散列函数，对查找项进行计算，测试下返回的槽号所对应的槽中是否有数据项即可。
实现了O（1）时间复杂度的查找算法。

这个方案的问题所在是这组数据相当凑巧，各自占据了不同槽。
假如还要保存44，h(44)=0，它跟77被分配到同一个0#槽中，这种情况称为 **“冲突collision”** ，我们后面会讨论到这个问题的解决方案。

# Python 简易求余散列实现
```python
# 定义散列函数 hash_func()
def hash_func(item: int, table_size: int) -> int:
    # 调用内置取模运算符 %，计算数据项对应的槽号
    return item % table_size

# 定义散列表初始化函数 create_hash_table()
def create_hash_table(size: int) -> list:
    # 构造长度为 size 且初始填充 None 的列表对象
    return [None] * size

# 定义数据插入函数 insert_item()
def insert_item(table: list, item: int) -> None:
    # 调用 len() 函数获取表长度属性
    slot = hash_func(item, len(table))
    # 访问 table 列表对象的对应索引位置，完成赋值
    table[slot] = item
```
# 冲突（Collision）与后续解决
## 什么是冲突
理想情况下每个数据项独占一个槽，但在实际场景中，不同数据项经过散列计算后可能输出完全相同的槽号。
这种多个键映射到同一槽位的现象称为 **冲突（Collision，又称哈希碰撞）**。
## 冲突解决预告
根据抽屉原理（鸽巢原理），当数据量或键空间大于散列表槽数时，冲突在数学上不可避免。
工程上常见的冲突处理方案包括：
**开放定址法（Open Addressing）**：当目标槽被占用时，按照某种探测规则（如线性探测、二次探测）在表中向后寻找下一个空闲槽位。
**链地址法（Chaining / 拉链法）**：散列表中的每一个槽不再仅保存单一数据，而是维护一个链表或其他动态集合，所有映射到同一槽位的数据项按序挂载在链表中。
